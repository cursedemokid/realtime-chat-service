# Как показать RabbitMQ в сервисе чатов

Сообщения пользователей принимаются через REST или SignalR и сохраняются в PostgreSQL. RabbitMQ используется для запроса внешнего уведомления получателю сообщения. Открытые клиенты получают обновление через SignalR.

```text
Alex отправляет сообщение
  → запись сообщения в PostgreSQL
  → SignalR: событие участникам разговора
  → RabbitMQ: notification.requested для Sam
  → demo.chat.notifications: очередь для наблюдения
```

## Запуск из интерфейса

На http://localhost:8030 выбрать **CHAT-009**, нажать «Запустить кейс». Страница создаёт привязку демоочереди, отправляет сообщение и проверяет полученное из брокера событие по ID сообщения. Успешное событие подтверждается и удаляется из очереди.

## Ручная демонстрация

1. В Swagger выполнить `POST /api/demo/rabbitmq/prepare`. В ответе придут имена exchange, queue и routing key.
2. Открыть **http://localhost:15673**. Демологин и пароль берутся из `.env`; значения примера — `demo` / `portfolio-local-only`.
3. В **Queues** открыть `demo.chat.notifications`.
4. Отправить новое сообщение из панели Alex или через API с его JWT.
5. Обновить очередь: счётчик Ready увеличится.
6. Получить событие через **Get messages** либо `POST /api/demo/rabbitmq/consume` в Swagger.

`consume` читает и подтверждает одно сообщение. Если есть старые события, повторить до события с нужным `messageId` внутри поля `Payload`. После получения очередного события Ready уменьшается.

## Топология и формат

| Поле | Значение по умолчанию |
| --- | --- |
| Exchange | `App.Events` |
| Тип exchange | `topic` |
| Routing key | `notification.requested` |
| Демоочередь | `demo.chat.notifications` |
| Content type | `application/json` |

Тело — JSON запроса уведомления: `EventId`, `UserId`, `NotificationType`, `Payload` и другие поля. Внутри строкового `Payload` находятся `conversationId`, `messageId` и отправитель. Этот publisher использует RabbitMQ.Client и обычный JSON. В проекте верификации используется MassTransit envelope с другим content type; форматы описаны в документации соответствующего проекта.

Демоочередь нужно привязать **до** отправки сообщения. Topic exchange маршрутизирует сообщение в существующие привязанные очереди. Полноценный сервис email/push мог бы подписаться своей очередью на тот же routing key.

Публикация внешних уведомлений сейчас best effort. При недоступности брокера сообщение чата сохраняется; гарантированная повторная доставка уведомления потребует outbox. Эта граница отражена в README.
